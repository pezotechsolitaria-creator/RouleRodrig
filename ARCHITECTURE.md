## 3. Architecture decisions (App Router + Turbopack, state, SW/PWA, canonical host, security headers)

### App Router + Turbopack

- **App Router** exclusively (`app/` directory; no `pages/`). Route handlers are `route.ts`; pages are `page.tsx`; layouts `layout.tsx`. Route groups used for the merchant portal: `app/merchant/(app)/`.
- **Turbopack** is the bundler for both dev and build (Next 16 default). `CLAUDE.md` records a real gotcha: **Turbopack dev lags on newly-added Tailwind arbitrary classes** (e.g. `h-[190px]`) until a full restart + SW cache clear — but `npm run build` generates all CSS, so always build-verify before pushing.
- Server Components by default; client components opt in with `"use client"` (all `context/*`, `QueryProvider`, interactive components).
- `reactStrictMode: true`, `poweredByHeader: false`, `productionBrowserSourceMaps: false` (`next.config.ts`).

### State management

Two distinct strategies, deliberately split:

- **React Context** (global app state, tourism site): mounted in `app/layout.tsx` in this nesting order — `LanguageProvider` → `CurrencyProvider` → `FavoritesProvider` → `CartProvider`. Each is a `"use client"` context in `context/*` or `lib/cart/CartContext.tsx`, backed by `localStorage`.
- **`@tanstack/react-query`** (server-state, **merchant portal only**): `components/merchant/QueryProvider.tsx` creates one `QueryClient` **per browser session** via `useState` (not a module singleton — avoids cross-user cache leakage on the server). Defaults: `staleTime: 30_000`, `retry: 1`, `refetchOnWindowFocus: false`. The account-less tourism site pays no react-query cost.

### Tailwind v4 design tokens

Design constraints codified in `DESIGN.md` ("Three-Voice Rule": Syne / DM Sans / Bebas only).

### Service worker & PWA

- **File**: `public/sw.js`. **Cache name**: `const CACHE = "rr-cache-v94"`. **`CLAUDE.md` mandates bumping `rr-cache-vNN` on every deploy** — skipping it strands users on a stale build.
- **Caching strategy** (correctness-first):
  - **Page navigations → network-first** (fresh HTML must match current `/_next` JS hashes; stale HTML → dead buttons/failed hydration). Falls back to cached page, then SHELL (`/`), then `Response.error()`.
  - **`/_next/static/*` (immutable hashed) → cache-first** (safe; URL changes when content changes).
  - **Everything else (images/fonts/map tiles) → network-first, cache fallback.**
  - `/admin` and `/api` are **never** intercepted; non-GET requests skipped.
- **Lifecycle**: `install` pre-caches SHELL + `skipWaiting()`; `activate` deletes all non-current caches + `clients.claim()`.
- **Registration**: `components/PWARegister.tsx` (mounted last in layout).
- **HTTP caching**: `next.config.ts` sets `/sw.js` → `Cache-Control: public, max-age=0, must-revalidate` so the SW itself is never stale-cached.
- **PWA manifest**: `app/manifest.ts` — `display: standalone`, portrait, `start_url: /?source=pwa`, dark theme, 192/512 icons (any + maskable).
- **Installed-app UX**: `app/layout.tsx` has a pre-hydration splash gate (shows only when launched standalone/A2HS, once per session, skips reduced-motion), captures Android `beforeinstallprompt` into `window.__rrInstallEvent`, and registers iOS `apple-touch-startup-image` launch images for common iPhone resolutions.
- **Mobile gotcha (from memory)**: dead-feeling buttons on mobile were caused by a stale SW serving old HTML + per-card gyro listeners — hence the network-first HTML rule and the cache-bump discipline.

### Canonical host & middleware

`middleware.ts` (matcher `['/((?!api|_next/static|_next/image).*)']`) does three things, in order:

1. **Canonical-host 308 redirect.** `CANONICAL_HOST` is derived from **`NEXT_PUBLIC_SITE_URL`** via `SITE_URL` in `lib/site.ts` (falls back to `https://roule-rodrig.vercel.app` when unset). The retired alias set is `RETIRED_HOSTS = { 'roule-rodrig.vercel.app' }`; a request to it is 308-redirected (permanent, method-preserving) to the canonical host, consolidating SEO signals onto `roulerodrig.com`. Preview deployments are intentionally **not** redirected. Because canonical tags, `sitemap.ts`, `robots.ts`, JSON-LD (`lib/schema.ts`), and email links all read the same `SITE_URL`, they can never disagree.
2. **`/admin` gate** — requires cookie **`rr_admin`**; otherwise redirect to `/admin/login` (login itself exempt). Belt-and-braces: `next.config.ts` also sends `X-Robots-Tag: noindex` for `/admin/*`.
3. **`/merchant` gate** — Supabase Auth via `updateSession(req)` (`lib/supabase/middleware.ts`); no user → redirect to `/merchant/login`. Session refresh is **scoped to `/merchant`** so the tourism site stays account-less and pays no auth cost.

### Security headers (`next.config.ts`)

Applied to every route via `async headers()`:

- **CSP**: `default-src 'self'`; `object-src 'none'`; `frame-ancestors 'none'`; `form-action 'self'`; `base-uri 'self'`. Permissive `img-src`/`connect-src` (`https:`) for Supabase Storage, QR images, map tiles. `'unsafe-inline'` retained on `style-src`/`script-src` (Next inline bootstrap + framer-motion inline styles; **no nonce pipeline yet — tracked as future hardening**). Explicit grants for PayPal (`*.paypal.com`, `paypalobjects.com`) and Vercel scripts (`va.vercel-scripts.com`, `vercel.live`).
- **Others**: `Strict-Transport-Security` (2y, preload), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (camera/mic off, geolocation self-only), `X-DNS-Prefetch-Control: on`.
- **Image optimization**: AVIF/WebP; remote hosts limited to `*.public.blob.vercel-storage.com`, `*.supabase.co`, `api.qrserver.com`.

### Build & deploy pipeline

- **Deploy**: `git push origin main` → **Vercel auto-deploys**. No separate deploy step (`CLAUDE.md`). `main` is treated as **live production** (`roulerodrig.com`).
- **Git remote**: `origin = https://github.com/pezotechsolitaria-creator/RouleRodrig.git` (verified via `git remote -v`). Current branch `main`; latest commit `83437ca M9: refuse to charge a total the customer was never shown (RR012)`.
- **Pre-push verification** (`CLAUDE.md`): (1) `npm run build` (generates all Tailwind CSS — the Turbopack-dev arbitrary-class lag does not affect production builds); (2) preview via in-app Browser tools, verifying layout with `getBoundingClientRect()` since screenshots time out; (3) PayPal creds are Vercel-only, so local `create-order` returns 503 (expected). Then **bump `rr-cache-vNN` in `public/sw.js`**.
- **Scheduled jobs**: `vercel.json` declares a Vercel Cron — `path: /api/cron/reminders`, `schedule: "0 6 * * *"` (daily 06:00 UTC). The handler is gated by `CRON_SECRET` (see §8).

### Database & migrations (summary)

- **`supabase/migrations/`** — 60+ timestamped SQL files, from `20260730000001_marketplace_core.sql` through the M9 series (`20260806101331_m9_expected_total_guard_correct_placement.sql`, `20260806103324_m9_status_paid_captures_payment.sql`). Themes: marketplace core, identity, producer/storage, `onboard_merchant` RPC, product RPCs, notifications/order status, **RLS + column-grant hardening** (M6–M9), delivery zones, store-hours scheduling engine, order-amounts single-source-of-truth, and payment-capture RPCs. **Full schema, RLS, RPCs, triggers, advisories → [DATABASE_SCHEMA.md](./DATABASE_SCHEMA.md).**
- **RLS/grant discipline** (memory + migration names): column `REVOKE`s are no-ops under a table grant and RLS never restricts columns, so status transitions and sensitive columns are locked behind **SECURITY DEFINER RPCs** (e.g. `update_order_status`, `create_order` v1→v4, `order_amounts`) rather than direct table writes.

## 4. Content model & i18n

### Content model — `site_content` JSONB (canonical)

This is the single most important architectural decision to understand before editing anything.

- **Storage**: Supabase table **`site_content`**, single row **`id = 'main'`**, column **`data` (JSONB)**, plus `updated_at`. Owner edits it in **`/admin`**.
- **Read path**: `getContent()` in `lib/content.ts` reads via a **cookie-free public read client** (`publicReadClient()` using `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` / `…_ANON_KEY`). Cookie-free reads keep every calling page **ISR-cacheable** rather than forcing it dynamic. `getContent()` **never throws** — on any error it falls back to `DEFAULT_CONTENT`, which is why it's safe in the root layout.
- **Merge/migration**: `mergeWithDefaults()` layers the stored partial over `DEFAULT_CONTENT` field-by-field, back-filling newly-added fields (e.g. fleet `available`/`units`/`category`, `contact.whatsappNumbers`) so old saved blobs never break the type.
- **Write path**: `saveContent()` uses the **privileged** client (`getPrivileged()` in `lib/supabase/admin.ts`) and `upsert`s the whole blob. Public anon role is **read-only** on `site_content` (anti-defacement).
- **`lib/defaults.ts` is seed-only**: it defines `DEFAULT_CONTENT`, `DEFAULT_QUICK_ACCESS`, `DEFAULT_HOME_CARDS`, and the entire `SiteContent` type surface (`HeroContent`, `FleetItem`, `MapLocation`, `FoodConciergeContent`, `RecommendedPlace`, etc.). **Editing `defaults.ts` does NOT change the live site** — the `site_content` row overrides it (confirmed in `CLAUDE.md` and the memory gotcha). Defaults only apply on first-run/fallback.
- **Do not patch content with raw SQL**: the admin "Save Changes" button overwrites the entire `data` blob, so ad-hoc SQL edits get clobbered.
- **Derived/live data** (not in `site_content`) is assembled in `lib/site-data.ts` → `getFleetView()`: it runs four Supabase reads **in parallel** (today's holds from `bookings`, 7-day recent bookings, approved `product_reviews` ratings, review cards) via `getPrivileged()`, computes `soldOutToday` per fleet item (island time = UTC+4), and is best-effort so the page never blocks.

### i18n — trilingual (en / fr / cr)

- **`Language = "en" | "fr" | "cr"`** (`lib/i18n.ts`). Kreol Rodrig is a first-class language.
- **Two translation surfaces**:
  1. **Static UI strings** — the large `translations` dictionary in `lib/i18n.ts` (1267 lines; `en`/`fr`/`cr` mirror each other). Consumed client-side via **`useLanguage()`** (`context/LanguageContext.tsx`) which exposes `{ language, setLanguage, t, hasChosen }` where `t = translations[language]`.
  2. **Admin-entered content** — resolved by **`loc(lang, base, fr, cr)`** in `lib/localize.ts`: content fields carry optional `*Fr`/`*Cr` siblings and fall back to the base (English) text when a translation is blank.
- **Language selection**: persisted in `localStorage` key **`rr_language`**. A pre-hydration inline `<script>` in `app/layout.tsx` auto-detects `navigator.language` and writes `rr_language` **before React mounts**, so the app boots straight into the visitor's language. The full-screen "choose your language" wall was deliberately **retired** (it was the homepage's Largest Contentful Paint per Lighthouse); the Navbar switcher still cycles languages. `LanguageContext` re-reads `rr_language` on mount (`suppressHydrationWarning` on `<html>` covers the server/client attribute mismatch).

## 6. Auth flows

### 6a. Admin authentication (the `rr_admin` password cookie)

The owner's admin is a **single shared password**, not a Supabase user. There is **no `auth.users` row for the admin**, which is why `is_platform_admin()` (SQL, keyed on `auth.uid()`) can never be true for it — the security boundary is `verifySession()` at the API layer, backed by the service-role client.

**Login** (`app/api/admin/login/route.ts` → `lib/auth.ts`):
1. Rate-limit `admin-login` 5 attempts / 5 min per IP.
2. `verifyPassword(input)` compares against `process.env.ADMIN_PASSWORD` using `crypto.timingSafeEqual` (length-checked first). In production a missing `ADMIN_PASSWORD` returns `''` → **denies all** auth (no insecure default); dev falls back to `admin2024`.
3. On success, set cookie `rr_admin = getSessionValue()`:
   - Token = `` `${issuedAt}.${hmac}` `` where `hmac = HMAC_SHA256(key, `${issuedAt}.${ADMIN_PASSWORD}`)`.
   - `key = process.env.SESSION_SECRET || SALT` (`SALT = 'roule-rodrigues-admin-2024'`). Rotating `SESSION_SECRET` invalidates all sessions; changing `ADMIN_PASSWORD` also invalidates them (it's bound into the HMAC).
   - Cookie flags: `httpOnly`, `secure` in prod, `sameSite:'lax'`, `maxAge = SESSION_TTL_MS/1000` (**30 days**), `path:'/'`.

**Verification** (`verifySession`, `lib/auth.ts`): Rejects if no cookie, if `ADMIN_PASSWORD` unset, if malformed, if `issuedAt` older than `SESSION_TTL_MS` (expired), if future-dated (> now + 60s), then constant-time compares against a freshly re-signed token.

**Two enforcement layers:**
- `middleware.ts` — for **page** routes under `/admin` (except `/admin/login`), redirects to `/admin/login` if the `rr_admin` cookie is merely **present** (existence check only, no signature verification — the API layer does the real verification). Note the middleware `matcher` **excludes `/api`**, so API routes are not protected by middleware.
- Each `app/api/admin/*` handler independently calls `verifySession()` (full HMAC + TTL check) before doing anything, then uses `getPrivileged()`.

**Logout** (`/api/admin/logout`): deletes the `rr_admin` cookie.

### 6b. Merchant / customer auth (real Supabase Auth)

**Supabase Auth is used** for merchants and customers (unlike admin). The `@supabase/ssr` cookie session flows through `lib/supabase/middleware.ts updateSession()`, scoped in `middleware.ts` to `/merchant` only (the tourism site pays no auth cost). `updateSession` calls `supabase.auth.getUser()` (re-validates the JWT, not just the cookie); unauthenticated `/merchant/*` (except `/merchant/login`) redirects to `/merchant/login`.

**Identity model** (`supabase/migrations/20260730000002_identity.sql`):
- `profiles` — one row per `auth.users` id (customers **and** merchant staff). Auto-created by the `on_auth_user_created` trigger (`handle_new_user()`, SECURITY DEFINER). RLS: self read/update; platform admins read all.
- `merchants` — a signed-in user may `INSERT` a merchant they own (`owner_id = auth.uid()`); every shop starts `status='pending'` and needs admin approval before `store_is_visible()`.
- `merchant_staff` — the `provision_merchant_owner()` trigger makes the creator `'owner'` staff on merchant INSERT. This table is the ownership anchor: `getMerchantDashboard()` / `getOwnStoreId()` resolve `merchant_id → stores.id` from the caller's staff membership; RLS (`staff_read`, etc.) enforces per-table.
- `platform_admins` + `is_platform_admin()` — a Supabase-Auth-based platform-admin concept exists in SQL, but the **cookie admin never has an `auth.uid()`**, so in practice platform administration is done through the cookie-gated `/api/admin/*` routes using the service-role client (see the explicit note in `app/api/admin/subscriptions/route.ts`).

**Merchant request pattern** (every merchant/customer route):
```
createClient() → auth.getUser() → 401 if no user
getOwnStoreId(supabase) → store_id from session (never from body)
supabase.rpc(...)  // RPC re-checks is_store_staff()/ownership itself
```
Writes go through SECURITY DEFINER RPCs (`onboard_merchant`, `create_product`, `add_product_media`, `create_order`, `update_order_status`, `confirm_order_payment`, `submit_payment_receipt`, `set_store_hours`) which re-verify ownership and use domain error codes (`RR001`–`RR012`, `P0001`) that the route maps to HTTP statuses. Marketplace uploads run **as the signed-in user** so Storage RLS (`is_store_staff` on the path's `store_id` segment) is the gate, not app code.

### 6c. Anonymous booking-insert model & `RR-` reference format

The public site is account-less for bookings. RLS lets `anon` **INSERT** into `bookings` / `place_bookings` but **not SELECT**. Therefore the routes:

1. Generate the id server-side: `const id = crypto.randomUUID();`
2. Insert the full record **without `.select()`** — an `INSERT … RETURNING` would trip the SELECT policy and break the booking. Vehicle bookings use `createClient()` (anon) for the insert; place bookings use `getPrivileged()`. The capacity/double-booking guard reads existing rows via `getPrivileged()` and `lib/holds.ts isActiveHold`.
3. Because the id is known up-front, it feeds the PayPal deposit flow and the reference.

**Booking reference** — one format everywhere (email, admin, `/manage-booking`, lookup):
```js
const bookingRef = "RR-" + id.replace(/-/g, "").slice(0, 6).toUpperCase();
```
i.e. `"RR-"` + first 6 hex chars of the UUID, upper-cased. Guest lookup (`/api/bookings/lookup`) normalises the entered ref and matches `id.replace(/-/g,'').startsWith(ref)` **and** `ilike email`, returning a safe summary only.

Server-computed money (never trusted from client): deposit % (scooter 25 %, car 50 %, resolved from `getContent().fleet` category), `delivery_fee` (sanitised), `deposit_amount = round(total_amount * pct / 100)`. Place deposits are the owner's flat `depositAmount` from the listing.

## 7. PayPal (EUR) order flow

`lib/paypal.ts` + `app/api/paypal/*`. PayPal does not support MUR, so deposits stored in Rupees are charged in **EUR**. Env-gated: `paypalConfigured()` requires `NEXT_PUBLIC_PAYPAL_CLIENT_ID` + `PAYPAL_SECRET`; `PAYPAL_ENV` selects `live` vs `sandbox` base URL. Locally these are only in Vercel, so create-order returns **503** (expected).

1. **Create** (`/api/paypal/create-order`): client sends only `{ bookingId, kind, mode }` — never a price. Route reads `deposit_amount`/`total_amount` from the stored `bookings`/`place_bookings` row. `mode:"full"` (vehicles only) charges `total_amount`; else the deposit. Blocks if `deposit_paid_at` already set (409) or if `isVehicleFree()` says another customer already paid (409, first-to-pay-wins).
2. **FX + fee**: `withPayPalFee(depositMur)` adds `PAYPAL_FEE_PERCENT` (customer bears the fee); `murToEur()` converts via a 1-hour-cached `open.er-api.com/v6/latest/USD` fetch (`eur/mur`), formatted to 2-dp. `createDepositOrder()` gets an OAuth token (`client_credentials`, Basic `CLIENT_ID:SECRET`) and POSTs `/v2/checkout/orders` with `intent:CAPTURE`, `reference_id = bookingId`, `amount {currency_code:"EUR"}`.
3. **Capture** (`/api/paypal/capture-order`): idempotent pre-check (already-paid → `{ok, alreadyPaid}`). Calls `captureOrder(orderID)`; **only** if PayPal returns `status === "COMPLETED"` does it patch `{ deposit_paid_at, paypal_capture_id, status:"confirmed" }`. The browser's "approved" is never trusted. Then (vehicles) it cancels other pending unpaid rivals whose dates are now full and emails them `sendVehicleUnavailableEmail` (no charge). Marketplace orders never reach this route.

## 8. Daily cron

`/api/cron/reminders` (`vercel.json`: `0 6 * * *` = 06:00 UTC). Auth: **requires** `Authorization: Bearer ${CRON_SECRET}` (Vercel Cron sends it automatically), via `authorizeCron()` in `lib/cron-auth.ts`. It **fails closed** — an unset `CRON_SECRET` returns 503 and the job does not run. It previously fell through to *open* when the variable was absent, leaving a publicly-scheduled endpoint that emails customers, WhatsApps the owner customer names and phone numbers, and cancels bookings callable by anyone. Also returns 503 without `SUPABASE_SERVICE_ROLE_KEY` rather than silently no-opping behind RLS. Uses `getPrivileged()`. Dates computed in island local time (UTC+4). Idempotent via per-row flags, which are now written **only when the send actually succeeded** (or there is no address), so a mail outage no longer buries a reminder permanently; failures are counted and turn the run non-2xx. Responsibilities:

- **Pickups tomorrow** (`start_date=tomorrow`, `pickup_reminded=false`): customer `sendPickupReminder` + owner `sendAdminPickupReminder`; set `pickup_reminded=true`.
- **Returns tomorrow** (`end_date=tomorrow`, `return_reminded=false`): `sendReturnReminder` + `sendAdminReturnReminder`; set `return_reminded=true`.
- **Feedback** (`end_date=yesterday`, status confirmed/completed, `feedback_reminded=false`): `sendFeedbackRequest`; set flag.
- **Release abandoned holds**: pending bookings older than `holdCutoffMs()` (default 48h, `HOLD_EXPIRY_HOURS`) **or** whose pickup day has passed → `status='cancelled'`.
- **Stay·Eat·Do** equivalents on `place_bookings` (`reminded`, `feedback_reminded`, stale-cancel).
- **Daily owner WhatsApp digest** (CallMeBot, owner only): deliver/collect/place lists for tomorrow.
- **Monday-only Ti Roulé miss digest** (`new Date().getUTCDay() === 1`): aggregates `lead_events` where `kind='tiroule_miss'` from the last 7 days and emails `OWNER_EMAIL` via `sendTiRouleMissesDigest` (unanswered-question digest → KB/SEO growth).
- **Nightly content backup**: snapshots `site_content.data` into `site_content_history` when changed; prunes history older than 90 days.

Returns a JSON counters summary (`pickupEmailsSent`, `holdsReleased`, `missesEmailed`, `backupSaved`, …).

## 10. Marketplace model & payment methods

### Business model & monetisation

The marketplace ("Local Store") is **subscription-based, not commission-based** (canonical rule i). Platform revenue is a recurring per-merchant subscription; nothing is skimmed per order.

- **Subscription tiers** — `subscription_plan` enum `('starter','standard','premium')` (`supabase/migrations/20260805100100_m6_subscriptions_payments_delivery.sql`). Labels in `lib/merchant/subscription.ts` (`PLAN_LABEL`). **Tier price points are NOT encoded anywhere** — `subscription_invoices.amount` is entered by the platform admin per renewal (`app/api/admin/subscriptions/route.ts`, `amount` field). Actual monthly prices per tier: **(to confirm)**.
- **Subscription status** — `subscription_status` enum `('trialing','active','past_due','suspended','cancelled')`. `trialing`/`active`/`past_due` = may sell; `suspended` = past grace, blocked; `cancelled` = merchant left.
- **Grace window** — `merchant_subscriptions.grace_days` (default 7). A merchant keeps selling until `current_period_end + grace_days`.
- **Authority gate** — SQL function `merchant_subscription_active(merchant uuid)` is the single source of truth; it gates `create_order()` and `quote_order()` (error `RR008`) and (per its header) product/shop writes. A merchant with **no** subscription row is treated as **active** (`coalesce(..., true)`) so pre-subscription merchants are never retroactively locked out. `lib/merchant/subscription.ts::getMerchantSubscription()` mirrors this rule for UI only and "never decides anything on its own."
- **Billing is admin/manual today** — no automated biller. `subscription_invoices` rows are written by `app/api/admin/subscriptions/route.ts` (actions: `approve_renewal`, `set_plan`, `start_trial`, `end_trial`, `suspend`, `reactivate`, `cancel`, `approve_merchant`). That route is gated by the **password-cookie admin** (`verifySession` / `COOKIE_NAME` in `lib/auth.ts`) + the **service-role** client, because `/admin` has no Supabase user so `is_platform_admin()` (which reads `platform_admins` by `auth.uid()`) can never be true for it.
- **Commission is dead but not yet removed** — `orders.commission_amount` and `merchants.commission_rate` still exist; `create_order()` writes `commission_amount = 0` to keep the NOT-NULL column valid. Nothing reads or displays it. Dropping the column is tracked as tech debt.

> **Doc/stale-code flags.** `MARKETPLACE.md` still describes the **old commission model** ("platform takes `merchant.commission_rate`… we net it and pay the merchant out") and lists **PayPal / MCB Juice checkout + QR pickup** as the marketplace payment flow. Both contradict the canonical rules and the shipped code. `MARKETPLACE.md` also references `app/api/marketplace/qr/redeem/route.ts` — **that route does not exist** (only `app/api/marketplace/route.ts` is present). Treat `MARKETPLACE.md` as an aspirational target document, not a description of current behaviour.

### Payment methods per flow

| Flow | Entry point | Allowed payment methods | Card / PayPal? | Settlement record |
|---|---|---|---|---|
| **Marketplace product order** | `POST /api/checkout` → `create_order()` (auth required) | `cash`, `bank_transfer`, `manual` | **Never** — money never touches the platform | `payments` row (MUR); merchant attests receipt |
| **Vehicle rental deposit/full** | `POST /api/bookings` then `POST /api/paypal/create-order` + `/capture-order` | PayPal (card) **or** offline bank transfer/cash | **Yes — PayPal only here** | `bookings.deposit_paid_at`, `bookings.paypal_capture_id` |
| **Stay·Eat·Do reservation** | `POST /api/place-bookings` then PayPal (`kind:"place"`) | PayPal deposit **or** request-only (no deposit) | **Yes — PayPal only here** | `place_bookings.deposit_paid_at`, `paypal_capture_id` |

Marketplace payment restriction (canonical rule ii) is enforced by **three independent gates**, none of which trusts the UI (`lib/schemas/checkout.ts` header):

1. **Zod** — `PAYMENT_PROVIDERS = ['cash','bank_transfer','manual']` (`lib/schemas/checkout.ts`).
2. **RPC whitelist** — `create_order()` raises `RR005` unless `p_provider in ('cash','bank_transfer','manual')` (`20260805120000_m6_create_order_v4_no_juice.sql`). The card-provider removal is documented in `20260805091000_create_order_reject_card_providers.sql`.
3. **CHECK constraint** — `payments_no_card_providers` on `payments` restricts `provider in ('cash','bank_transfer','manual')` (`20260805115000_m6_remove_mcb_juice.sql`).

`payment_provider` enum still contains legacy `'paypal'` and `'mcb_juice'` values (Postgres has no `DROP VALUE`) but they are **unreachable** for marketplace orders. MCB Juice was fully removed as a merchant method.

**QR** in the PAYMENT sense is a merchant-supplied static image, not a redeemable token: `store_payment_settings.qr_image_url` / `qr_label`. The PICKUP handoff is live as of M28, but as an 8-character code rather than a scanned QR: `qr_pickup_tokens.code` is issued by a trigger when an order reaches `ready_for_pickup`, shown on `/orders/[id]` and `/orders/track`, and redeemed by store staff at `/api/merchant/pickup/redeem` → `redeem_pickup_code()`, which is single-use, expiring, staff-only and idempotent.

## 11. Pricing & deposit rules

### Vehicle bookings (`app/api/bookings/route.ts`)

Deposit % is derived **server-side** from the resolved fleet category, never trusted from the client:

- Scooter (default): **25%**; Car: **50%** (`depositPct = 50` when `item.category === 'car'`).
- `deposit_amount = Math.round(total_amount * depositPct / 100)`, stored with `deposit_pct`.
- Delivery fee: scooter **Rs 400**, car **0** — only accepted if a sane non-negative integer, else stored `null` (`delivery_fee`).
- PayPal may charge the **deposit or the full total** (`mode: 'full' | 'deposit'` in `app/api/paypal/create-order/route.ts`); the amount is always re-read from the stored booking (`deposit_amount` / `total_amount`), never from the request body.

### Stay·Eat·Do (`app/api/place-bookings/route.ts`)

**Owner-set flat deposit** resolved from the listing (`item.depositAmount`), floored at 0 and rounded: `deposit_amount = depositAmount > 0 ? depositAmount : null`. `>0` → deposit-to-confirm; `0/absent` → request-only. The client can never lower it.

### PayPal / EUR (`lib/paypal.ts`, `lib/site.ts`)

PayPal has no MUR, so deposits (held in Rs) are charged in **EUR** (`PAYPAL_CURRENCY = "EUR"`):

- Rs→EUR from live rates (`https://open.er-api.com/v6/latest/USD`, `eur/mur`), cached 1h, server-side; `murToEur()` rounds to 2 dp. Never fabricates a rate.
- The customer bears the PayPal fee: `withPayPalFee()` adds `PAYPAL_FEE_PERCENT` (env `NEXT_PUBLIC_PAYPAL_FEE_PERCENT`, default **4%**) on top of the deposit; shown, never hidden.
- Env-gated: no `NEXT_PUBLIC_PAYPAL_CLIENT_ID` + `PAYPAL_SECRET` → `paypalConfigured()` false → routes **503**, no button renders. `PAYPAL_ENV=live|sandbox` selects the API base.

### Marketplace pricing

`order_amounts(p_store_id, p_subtotal, p_fulfillment, p_zone_id)` is the **single source of truth for pricing policy**, called by both `create_order()` (charges) and `quote_order()` (displays) so the shown figure and the charged figure cannot drift (`20260805130000_..._single_source_of_truth.sql`, zone-aware in `20260805171232_m7_order_amounts_by_zone.sql`):

- **Tax**: `0` if `stores.tax_inclusive`, else `round(subtotal * stores.default_tax_rate)`.
- **Delivery**: only `rr_delivery` is charged; `pickup` and `customer_delivery` are free. Fee is read from `delivery_zones.fee` by `p_zone_id` (canonical rule iii, GPS/zone-based; `20260805171151_m7_delivery_zones.sql`). Requires `marketplace_settings.delivery_enabled`. Zones seeded at Rs 150 flat; owner sets real per-zone fees. The fee is snapshotted onto `orders.delivery_fee` / `orders.delivery_zone_id` so re-pricing a zone never rewrites history.
- **GPS** (`orders.delivery_lat/lng`) is captured for navigation but **never** used for pricing; zone is chosen explicitly (small irregular Rodrigues localities → nearest-centroid would mis-price boundaries).
- Subtotal is deliberately **not** computed in `order_amounts()`: `create_order()` derives it inside its row-locking loop (what makes overselling impossible) while `quote_order()` reads prices unlocked.

### Money handling (`lib/money.ts`)

All money is **integer minor units**. `toCents()` parses a decimal string entirely in string/integer space (avoids the IEEE-754 `9.995*100 === 999.4999…` misround), rejecting anything over `MAX_CENTS = 2_147_483_647` (int4). Display-only FX helpers (`lib/currency.ts` fixed rates with `~`, `lib/currency-convert.ts` live+estimate) are for tourist price display and Ti Roulé chat — never for charging.

### Booking reference & marketplace order-number formats

Two **distinct** identifiers — do not conflate:

| Kind | Format | Source | Where |
|---|---|---|---|
| **Vehicle / place booking ref** | `"RR-" + id.replace(/-/g,"").slice(0,6).toUpperCase()` (first 6 hex of the UUID) | derived in the route from `crypto.randomUUID()` | `app/api/bookings/route.ts`, `app/api/place-bookings/route.ts`, emails, `/manage-booking`, capture-order rival emails |
| **Marketplace order number** | `'RR' \|\| YYMMDD \|\| '-' \|\| upper(substr(md5(random()), 1, 5))` (e.g. `RR260806-A1B2C`) | generated inside `create_order()` | `orders.order_number` (unique) |

### Holds, expiry & abandoned-checkout release

**Bookings** (`lib/holds.ts`):

- `HOLD_EXPIRY_HOURS` env (default **48**); `holdExpiryHours()` guards against non-finite/≤0. `holdCutoffMs()` = now − window.
- `isActiveHold(row)` decides whether a pending row still reserves its dates:
  - `confirmed` → always holds.
  - **Payment-gated** rows (a deposit is due — all vehicle bookings, and any place booking whose listing has `deposit_amount > 0`): **only a paid deposit holds** (`!!deposit_paid_at`). An unpaid pending request never blocks others → **first-to-pay-wins**.
  - **Request-only** place bookings (no deposit): a pending hold counts until the 48h window passes.
  - The distinction is inferred structurally: vehicle selects carry `deposit_paid_at` but not `deposit_amount` (payment-gated); place selects carry both.
- Read-time enforcement frees dates the instant the window passes (no wait for cron); a daily cron flips expired pending rows to `cancelled` for tidiness.
- **First-to-pay-wins** is completed at capture: `app/api/paypal/capture-order/route.ts` releases other pending unpaid rivals whose dates are now full (`isVehicleFree()` in `lib/availability.ts`) and emails them (`sendVehicleUnavailableEmail`). `create-order` also refuses to start a payment for a vehicle already secured for those dates (409).

**Marketplace orders** use a different mechanism — `orders.auto_release_at` (set to `now() + 48h` at creation). `create_order()`'s sweep only releases rows still in `pending_payment` **and** past `auto_release_at`; `submit_payment_receipt()` **nulls `auto_release_at`** the moment a customer reports payment, so an order backed by real money is never auto-cancelled (`20260805100400_m6_manual_payment_handshake.sql`). Released stock is returned via `inventory_movements` (`reason='restock'`).

### Marketplace order lifecycle & manual-payment handshake

Money never touches the platform, so only the **merchant** can attest receipt (`20260805100400_m6_manual_payment_handshake.sql`):

1. `create_order()` → `orders.status = 'pending_payment'`, `payments.status = 'pending'`, stock reserved under row lock.
2. Customer: `submit_payment_receipt(order_id, receipt_path)` → `awaiting_payment_confirmation`, nulls `auto_release_at`. Receipt path must live under `^<order_id>/` (prevents pointing at another customer's uploaded proof); `require_receipt` shops must attach one. Same "Order not found" for missing/foreign orders (no id probing).
3. Merchant: `confirm_order_payment(order_id)` (via `POST /api/merchant/orders/[id]/confirm-payment`) → `payments.status='captured'`, `orders.status='paid'`. Re-checks `is_store_staff()` itself (route is a thin wrapper). Accepts `pending_payment` too (cash paid at handover).

**Invariant repair** (`20260806103324_m9_status_paid_captures_payment.sql`): a second "Confirm payment received" button routed through `update_order_status → 'paid'` left `payments.status='pending'` — permanently divergent (revenue undercounts; `confirm_order_payment` then refuses). Fixed at root: any transition **into `'paid'`** now captures the still-pending payment in the same locked statement, and existing diverged rows were repaired.

## 12. Security rules & invariants

### Price-integrity rule (RR012) and enforcement

**Rule**: server-derived pricing is necessary but not sufficient — the amount charged **must equal what the customer was shown** (canonical rule iv). Demonstrated live: quoted Rs 170, platform re-priced a zone, order created for Rs 520 with no warning — worst case under bank transfer, where the shown figure is what the customer wires.

**Mechanism**:

- The checkout UI displays the authoritative `quote_order()` total (`POST /api/checkout/quote`), never a client-computed figure.
- `POST /api/checkout` forwards the customer-visible total as `expectedTotal` → `create_order(p_expected_total)` (`lib/schemas/checkout.ts`: `expectedTotal` int, `0 … 2_147_483_647`; passthrough in `app/api/checkout/route.ts`).
- Inside `create_order()`: after `v_total` is finalised and **before** the payments row is written, `if p_expected_total is not null and p_expected_total <> v_total then raise RR012`. Raising rolls back the already-inserted order row, so a moved price yields **no order at all** rather than a surprise charge.
- **Not a price lock** — the DB still decides the price; RR012 only refuses a purchase the customer did not agree to. Optional, so any caller that omits it still works; the checkout route always sends it.

**Placement bug worth knowing** (`20260806101331_m9_expected_total_guard_correct_placement.sql`): the first attempt (`20260806101132`) put the check where `v_total` was still `0`, so it refused every checkout that sent an `expectedTotal` (and gave the wrong "it is now Rs 0.00" message). The corrected guard sits immediately before the order-number generation / payments insert. Route maps RR012 → **409 with `code`** so the form re-quotes and shows the new figure.

### Anon-insert security model (RLS)

Canonical rule v: **anon may only INSERT pending rows, never SELECT**. Because an `INSERT … RETURNING` (`.insert().select()`) trips the missing SELECT policy and breaks the whole insert, the server **generates `crypto.randomUUID()` up front and inserts plainly**, then derives everything it needs (booking ref, PayPal handoff) from that id without reading the row back.

- Confirmed in `app/api/bookings/route.ts` (`const id = crypto.randomUUID(); … .from("bookings").insert([record])`), `app/api/place-bookings/route.ts`, and `app/api/leads/route.ts` (`lead_events`, "insert-only; no PII"). Same pattern applies to `contact_submissions`, `waitlist`.
- **Insert-only anon tables**: `bookings`, `place_bookings`, `contact_submissions`, `waitlist`, `lead_events`. Note: these belong to the **tourism/booking schema, whose migrations are NOT in `supabase/migrations/`** (that folder is marketplace-only). Their RLS lives in the Supabase project directly — **(to confirm against the live DB)**; the pattern is asserted by `CLAUDE.md` and every route above.
- **Client selection**: `place_bookings` uses the **service-role** client (`getPrivileged()`, `lib/supabase/admin.ts`) for its capacity guard (which needs to read other pending rows); `bookings` uses `getPrivileged()` for the double-booking guard but the anon `createClient()` for the actual insert; `lead_events` uses the anon `createClient()`.
- **Marketplace orders are the exception**: `POST /api/checkout` requires an authenticated Supabase user (`supabase.auth.getUser()` → 401), and `create_order()` is `revoke … from public, anon; grant … to authenticated`. Marketplace order rows are created by the RPC under `auth.uid()`, not by anon insert.

### Column-grant lockdowns

Canonical rule vi — a column REVOKE is a no-op under a table grant; RLS never restricts columns. Handled by dropping the table SELECT and re-granting an explicit column list:

- `orders.internal_notes` withheld: `20260805174857_m7_orders_column_select_lockdown.sql` — revokes table `SELECT` (and `DELETE`/`TRUNCATE`) from `anon, authenticated`, re-grants all columns **except** `internal_notes`. Maintenance hazard: a new `orders` column is unreadable until explicitly granted (reads fail `42501`).
- `store_payment_settings` bank fields (`bank_name`, `account_holder`, `account_number`, `payment_instructions`) withheld: `20260806092433_m8_bank_details_order_scoped.sql` — same technique, plus a `store_bank_details(p_store_id)` SECURITY DEFINER accessor that returns them only to store staff, admins, or a customer **who already has an order at that shop**.
- `TRUNCATE` revoked from app roles marketplace-wide (`20260806025240_m8_revoke_truncate_from_app_roles.sql`) — TRUNCATE bypasses RLS entirely, so leaving it granted meant RLS was not the last line of defence.

### Security gotchas & invariants

- **`.insert().select()` is forbidden on anon tables** — RLS allows INSERT, not SELECT; the `RETURNING` clause silently breaks the whole insert. Generate the UUID server-side and insert plainly.
- **Column REVOKE is a no-op under a table grant** — to hide one column you must revoke the table SELECT and re-grant the explicit column list (or expose a SECURITY DEFINER accessor). Adding an `orders` / `store_payment_settings` column later makes it unreadable (`42501`) until granted.
- **`/api/checkout` is a thin pass-through, not a trust boundary** — every price, stock, subscription, fulfilment, payment-method and schedule check is re-done inside `create_order()` under a row lock. The client is trusted only for "which variants, how many, how to pay/receive."
- **PayPal amounts are always re-read from the stored booking** — the client sends only `bookingId` (+ `kind`/`mode`); it can never dictate a smaller deposit.
- **Removed `kind:"order"` PayPal branch was a P0** (`app/api/paypal/capture-order/route.ts` header) — that route is deliberately **unauthenticated** (PayPal approval is the only credential) and holds a **service-role** client; an anonymous caller who knew an order UUID could force a capture failure and trigger `mark_order_payment_failed()` on someone else's order, cancelling it and dumping its stock. Marketplace orders must never reach PayPal at all.
- **Two admin identities** — `/admin` (password-cookie, no Supabase user) vs `platform_admins` (Supabase `auth.uid()`). Cookie-admin routes must gate on `verifySession()` then use the **service-role** client; `is_platform_admin()` is always false for them. `getPrivileged()` silently falls back to the anon client when `SUPABASE_SERVICE_ROLE_KEY` is unset — the admin subscriptions route guards with `hasServiceRole()` and returns **503** rather than a misleading 500 (or half-succeeding read).
- **Every superseded RPC overload is dropped** — each `create_order` / `order_amounts` / `quote_order` migration `drop function`s the old signature so nothing can bind to unguarded (zone-unaware, RR012-less, card-accepting) pricing.
- **`update_order_status`/`mark_order_paid` are RPC-only and revoked from `authenticated`** — orders can't be mutated by direct table writes.
- **`payments.currency` may differ from `orders.currency`** — marketplace `payments.amount` is the MUR `v_total`; PayPal captures (vehicle/place) are EUR and recorded on `bookings.paypal_capture_id`, not `payments`.
- **RR012 depends on the UI sending `expectedTotal`** — a caller that omits it gets server-derived pricing with **no** "did the customer see this?" guarantee. The checkout route always sends it; any new checkout path must too.
- **`store_schedule_status()` gates checkout** (`RR010` shop closed, `RR011` delivery window) — `cart/resolve` and `quote` mirror it so the UI never offers an option the RPC will refuse; `store_payment_settings` defaults (`accepts_cash` on, `accepts_bank_transfer` off, `offers_rr_delivery`) are mirrored client-side to match `create_order()`'s `RR009` gate.

### Notable security observations (for the incoming engineer)

- **`/api/owner-upload` is unauthenticated** and writes to the private `applications` bucket via the service-role client (only rate-limited 15/60s, 4 MB, magic-byte checked). Anyone can deposit files there; worth confirming that's intended.
- **Rate limiting is in-memory and per-serverless-instance** (`lib/rate-limit.ts`) — not globally consistent. `admin-login` (5/5min) and booking guards are per-instance. `@vercel/kv` is installed but not wired in.
- **Admin is a single shared password** with a 30-day cookie; there's no per-user admin identity, no audit trail of which human acted, and no lockout beyond the per-IP login limiter.
- **`getPrivileged()` silently degrades** to the anon client when `SUPABASE_SERVICE_ROLE_KEY` is unset; only the subscription/store admin routes fail loudly (`hasServiceRole()` → 503). Other admin routes would behave differently (RLS-limited) if the key were missing.
- **Middleware does not verify the admin cookie signature** (existence-only) and **excludes `/api`** — the real gate is each API handler's `verifySession()`. A route that forgot to call it would be unprotected; all audited ones call it.
